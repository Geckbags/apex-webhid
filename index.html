Per-key colour table

      

        This is a separate feature from the effect engine. It is a
        static colour per key, used when the board is in its per-key/custom mode.
        It does not change the effect, brightness or speed above.
        


        Every byte is named from assembly (§8.13.2): byte 0 = the first
        keyItem, then (light, R, G, B) per key in ascending order.
        The command is 0x11; the table is read with 0x16
        first, untouched keys are preserved, and the write is split into 14-key
        pages exactly as the app's builder does. The whole table is read back and
        compared afterwards.
      

      

        
        
        
      

      

        Write 0x11 — read-modify-write against 0x16,
        then full-table readback verification. Colour is recoverable by rewriting,
        unlike keymap layout or actuation records.
      

      

    

  


  
  

    

      
Profiles

      

        
      

      

        
        
        
        
      

      

        ⚠️ Profile writes (0x55/0x58/0x59) are exposed but can permanently change device state; only recovery is factory reset. Always take a snapshot first.
      

      

        The Windows app's Export and Import profile buttons are
        host-side file handling, not protocol operations: export dumps what these
        four commands read back, and import replays the corresponding writes. A
        correct import is therefore only as safe as the writes it performs.
      

      

    


    

      
Device snapshot

      

        
        
        read-only — writes nothing
      

      

        Reads all ten of the device's configuration tables in one pass and shows
        them decoded. This mirrors what the Windows app's
        SyncConfigUtil collects before it pushes a configuration back
        (PROTOCOL.md 8.17).
        


        Take one before changing anything. Writes to this board
        can only be recovered with a factory reset, which discards every profile
        and binding. This snapshot is the only record of the current state that
        can be made from the host.
        


        Every call is a read. Nothing here can damage the device, and the JSON is
        plain text you can keep or diff.

Key map

      

        
        
        read-only
      

      

        The per-key remap table, the same data behind the Windows app's
        KeySetForm. Records are 3 bytes and the third is a HID usage
        ID, so entries decode to real key names; anything unmapped stays numeric
        rather than being guessed.
        


        Writes are not offered: 0x20 and 0x24 are two
        distinct functions that the app logs under the same name, and neither is
        yet attributable to a UI action (see §3.3).
      

      

        
        
        compare one read against another
      

      

        A read alone cannot tell you which keys are remapped: the record carries
        no changed flag, and a key index is not a HID usage. Read the board, set
        that as the reference, change something, then read again — the keys
        that differ are listed.
        


        keyItem is implied by position and never sent; the three wire
        bytes are type, hValue, lValue
        (§8.19).
      

      

      

    


    

      
Macros

      

        
        
      


      

        
          
#KeyActionDelay (ms)

        
        
      

      

        
        
        
        
        
      


      

        Ten slots, M1–M10, matching the Windows app's macro editor. Each step is
        one 6-byte record —
        type, state, lValue, hValue,
        and a 16-bit little-endian time in milliseconds. The key is a
        HID usage split across lValue/hValue, and
        state is 1 for down, 0 for up.
        


        Bytes 0 and 1 are transposed on the wire. This form works in
        struct order and the driver applies the transposition, so what you
        see here is what is stored.
        


        The field names come from the key_macro_table DDL that the app
        ships inside GameKeyboard.exe to persist exactly this data
        (PROTOCOL.md 8.12).
      

      

    


    

      
Fn layer and advanced modifiers

      

        
        
        
        
        
      

      

        
        
        
      

      

        ⚠️ Fn-layer writes (0x22/0x23/0x25) modify bindings; take a snapshot before changes.
      

      

      

        The Windows app's HighKeyForm stores six advanced per-key
        modifiers here — DKS (Dynamic Key Stroke),
        MT (Hold/Click), TGL (Toggle),
        RS (Radial Sensing),
        SOCD (Simultaneous Opposing Cardinal Directions, with four
        resolution modes) and OKS (Key Override on Release).
        They live in these bindings rather than in the plain keymap, so a driver
        that only exposes keycodes cannot express them.
        


        Every modifier's record code and length are decoded
        (PROTOCOL.md §8.3.2). The codes do not run in label order:
        TGL=0, MT=1, DKS=2, RS=3, OKS=4, SOCD=5, while the app lays
        the dialogs out as DKS, MT, TGL, RS, SOCD, OKS. SOCD is fully specified
        (key, type, key1, key2, resolution mode); the other modifiers' data bytes
        are still unnamed, so those stay a raw hex field.
      

      

    
  


  
  

    

      
Actuation points

      

        Product table ranges: trigger 10–359, quick-trigger release 4–330, reset 4–330.
      

      

        
        
        
      

      

        
        
        
        
      

      

        ⛔ WRITING ACTUATION POINTS IS DISABLED. The decompiled frame builders show 0x26, 0x27 and 0x28 are paged writes. The per-record byte permutation is partially known but not safely reconstructable from static analysis alone — a wrong write can corrupt your layout and is only recoverable by a factory reset. DO NOT ENABLE WRITES without live capture against real hardware and verification. Reads above are safe.
